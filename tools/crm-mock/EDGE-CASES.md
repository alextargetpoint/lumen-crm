# Вариации CRM-синка — матрица для публичного запуска

Что может прийти/сломаться при подключении реальных amoCRM / Bitrix, и как мы это держим.
Статусы: ✅ закрыто и покрыто тестом · ⚠️ открыто (риск) · 📋 дизайн для Bitrix · ➖ сознательно не делаем.

Прогон всех ✅: `node tools/crm-mock/roundtrip.js` (28 проверок, 12 сценариев).

---

## A. Авторизация и связь
| # | Вариация | Риск | Статус |
|---|----------|------|--------|
| A1 | Неверный/пустой токен | молчаливый «подключён» при мёртвой связи | ✅ 401 → `connected:false`, `lastOkAt=0`; UI не врёт |
| A2 | Токен отозвали/сменили в процессе | авто-синк долбит мёртвый конфиг | ✅ при провале снимаем connected → тик затихает до ручного переподключения |
| A3 | Rate-limit (amo 7 rps, Bitrix 2 rps) → 429 | потеря пуша, бан | ✅ ретрай с бэк-оффом, уважаем `Retry-After` |
| A4 | Таймаут/зависшее соединение | хендлер висит вечно | ✅ `setTimeout` 20с на запрос + ретрай |
| A5 | 5xx / тех-работы amo | сбой синка | ✅ ретрай 5xx |
| A6 | Неверный поддомен | DNS-ошибка | ✅ ловится как сетевая → ретрай → ошибка в UI |
| A7 | 402 (аккаунт amo не оплачен) | — | ⚠️ сейчас как generic-ошибка; стоит отдельный текст владельцу |
| A8 | Параллельные синки (ручной + авто-тик) | двойной пуш/дубли | ✅ лок по тенанту (409 ручному, тик пропускает) |

## C. Логика синка и состояние
| # | Вариация | Риск | Статус |
|---|----------|------|--------|
| C1 | Первый синк большой базы (10k) | 10k запросов, rate-limit, таймаут UI | ✅ батч ≤50 → ~200 запросов; durable amoId после каждого батча |
| C2 | Дубликат в amo (лид уже заведён руками) | второй дубль | ✅ дедуп по телефону перед созданием (усыновляем) |
| C3 | >1 страница изменений в пулле | теряем хвост | ✅ пагинация page-loop (тест: лимит 5, 12 лидов) |
| C4 | Рассинхрон часов клиент/amo | пропуск/лишнее в пулле | ✅ overlap-окно на `since` (−2 мин) + applyPulled идемпотентен |
| C5 | Сделку удалили в amo (у нас висит amoId) | update → 404 навсегда | ✅ 404 → сброс amoId → пересоздание |
| C6 | Эхо-петля (наш пуш → amo updated → пулл назад) | бесконечный цикл | ✅ applyPulled меняет только отличающееся; стадию==стадия → no-op |
| C7 | Краш между create и сохранением amoId | дубль при рестарте | ✅ `save`-колбэк (saveNow) после каждого создания |
| C8 | Конфликт: правка в Lumen и в amo одновременно | кто победит | ⚠️ сейчас: пуш, затем пулл перезапишет стадию если `pullStages`. Документировано; при жалобах — поле «источник правды» на стадию |
| C9 | Частичный провал батча | потеря хороших лидов | ✅ изоляция: батч 400 → поштучно, битый в `_amoErr`, остальные уходят |
| C10 | Свои непустые квалы vs данные из amo | затирание своей квалификации | ✅ applyPulled НЕ трогает непустые `quals.*.value` |

## E. Bitrix24 — дизайн (модуль ещё не построен) 📋
Та же архитектура (чистая логика + инъектируемый адаптер + мок). Ключевые отличия от amo, которые закладываем сразу:
- **Подключение:** входящий вебхук `https://portal.bitrix24.ru/rest/{uid}/{token}/` — токен в URL, OAuth не нужен (проще amo). Храним как секрет, стрипаем из publicSettings.
- **Сущности:** Lumen-лид → **Bitrix Deal** (crm.deal), не Lead. У Bitrix две сущности (Lead→Deal); «простой режим» = только Deals. Deal универсальнее → маппим в Deal; опционально Lead.
- **Стадии:** `STAGE_ID` вида `C1:NEW` (с префиксом категории/воронки `CATEGORY_ID`). statusMap: lumenStage → `C{cat}:{stage}`.
- **Поля:** `UF_CRM_xxx`. Список/enum — через `crm.deal.fields` (аналог нашего авто-детекта).
- **Телефон:** мультиполе контакта `PHONE: [{VALUE, VALUE_TYPE:'WORK'}]`.
- **Rate-limit:** 2 rps (строже amo) → батчи через метод `batch` (до 50 команд в одном вызове) + наш бэк-офф.
- **Пагинация:** `start` offset (по 50), ответ `next`.
- **Методы:** `crm.deal.add/update/list`, `crm.contact.add`, `crm.deal.fields`, `crm.status.list` (стадии), `batch`.
- Всё остальное (дедуп, 404→пересоздание, опт-аут, overlap, лок, enum) переносится 1:1 — логика общая, различается только адаптер и формат ID.

## Открытые хвосты (не блокеры запуска, зафиксированы)
- A7 отдельный текст на 402 · B8 валидация status_id при сохранении конфига · C8 политика конфликта стадии · D3 ответственный-менеджер · D5 вебхуки-от-amo для near-realtime.
- UI: маппинг пока «голые» id (select-поля авто-детектятся на бэке); при желании — визуальный маппинг с подтягиванием списка полей из amo по кнопке.
