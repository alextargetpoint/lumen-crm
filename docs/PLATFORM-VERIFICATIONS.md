## 4. Instagram — анализ контента + аналитика (пробел, расписано полностью)

Чтобы Lumen читал контент агентства в Instagram и забирал аналитику, агентство подключает свой **Instagram Professional** аккаунт (Business или Creator), **связанный с Facebook-страницей**, через **Facebook Login**.

**Предусловия у агентства:** IG переведён в Professional и привязан к FB-Page. Иначе Graph API его не увидит.

**Права (App Review, Advanced Access):**
- `instagram_basic` — профиль и медиа (посты, Reels).
- `instagram_manage_insights` — аналитика (охваты, вовлечённость, показы).
- `pages_show_list`, `pages_read_engagement` — доступ к связанной Page.
- `business_management` — работа в контексте бизнеса агентства.
- (для публикации Reels/Stories дополнительно) `instagram_content_publish`.

**Как проходит:**
1. В приложении Meta добавить продукты **Facebook Login** и **Instagram Graph API**.
2. Facebook Login → настроить: Valid OAuth Redirect URIs (наш колбэк), Privacy Policy URL (`/privacy.html`), User Data Deletion (`/data-deletion.html`).
3. Собрать рабочий демо-поток: «агентство жмёт Подключить Instagram → логин FB → выбор Page/IG → мы показываем его посты и аналитику в Lumen».
4. App Review: на каждое право — обоснование (зачем) + скринкаст этого сценария + тестовый доступ ревьюеру.
5. Обоснование (шаблон): «Наши пользователи — агентства недвижимости. Они подключают собственный Instagram Business, чтобы внутри Lumen видеть свои опубликованные материалы и их аналитику для планирования контента. Данные используются только внутри аккаунта агентства, не передаются третьим лицам».

Всё это — то же приложение Meta и та же Business Verification, что и для WhatsApp/Ads. Отдельной компании-проверки не нужно.

## 6. Google — синхронизация календаря (пробел, расписано полностью)

Для синка Google-календаря нужна проверка Google OAuth. Это отдельный трек от Meta.

1. **Google Cloud project** → включить **Google Calendar API**.
2. **OAuth consent screen**: тип External, заполнить: название приложения, лого, домашняя страница (`lumen247.com`), Privacy Policy (`/privacy.html`), Terms (`/terms.html`), authorized domains, контактные e-mail.
3. **Scopes**: брать **минимально достаточные**.
   - `https://www.googleapis.com/auth/calendar.events` (события) или `.../auth/calendar` — это **sensitive scope** → нужна верификация Google, но БЕЗ дорогого аудита.
   - ⛔ **Не брать Gmail-scope на чтение писем** (`.../auth/gmail.readonly` и подобные) — это **restricted scope**, который тянет за собой **ежегодный аудит безопасности CASA** (сторонний платный аудит, недели работы). Если функция «читать почту» не критична — не запрашиваем и экономим кучу времени/денег.
4. **Domain verification** в Google Search Console (подтвердить `lumen247.com`) — обязательно для верификации consent screen.
5. **Submit for verification**: Google запросит демо-видео (как пользователь даёт доступ и что мы делаем с данными), описание использования каждого scope, ссылку на политику.
6. Пока не верифицировано — приложение работает в режиме Testing (до 100 тест-юзеров, экран «непроверенное приложение»). Для боевого множества агентств нужна пройденная верификация.

Сроки: sensitive scope — обычно дни-недели. Если случайно возьмёшь restricted (Gmail) — месяцы + CASA. Поэтому **для календаря берём только calendar scope**.

**Apple/iCloud-календарь** — проще: подключается по **CalDAV** с **app-specific password** (пользователь генерирует в настройках Apple ID). Формальной верификации/ревью нет. Хороший «безбюрократический» вариант календаря на старте.

## 10. Частые причины отказов (общее для всех)

- Данные компании в заявке ≠ данные в документе (адрес/название) → всё строго как в Visura.
- Запросили больше прав, чем показали в демо → просить только то, что реально демонстрируем.
- Нет рабочего демо-потока/тестового доступа → ревьюер не смог повторить сценарий.
- Нерабочие или заглушечные Privacy/Terms/Data-Deletion ссылки → все страницы должны открываться на боевом домене.
- Google: взяли restricted scope (Gmail) без нужды → лишний аудит CASA. Берём минимум.
