# Lumen — инфраструктура авторизации, аккаунтов и сохранности данных

Обновлено: 14 сентября 2026. Это канонический документ по всему, что связано с входом, регистрацией,
хранением аккаунтов и защитой данных. **Перед любой правкой логина/сессий/хранения — читать этот файл
и раздел «Правила безопасных изменений».** Цель: в открытом SaaS с боевыми данными клиентов НИКОГДА
не повторить крах дашборда (правка приватности/входа → система легла → восстановление = ад).

---

## 1. Модель аккаунтов

Три типа арендатора (тенант = агентство, свой файл БД):
- **Агентство (agency)** — владелец (owner) + сотрудники (brokers). `settings.agency.edition != 'solo'`.
- **Соло-брокер (solo)** — один человек, без команды. `settings.agency.edition = 'solo'`.
- Внутри агентства: **owner** (полные права) и **broker** (права по `roleType` → `ROLE_CAPS`, видимость лидов own/all, фильтры по тегам/источникам).

Хранение секретов аккаунта (per-tenant, в `db.json`):
- Владелец: `settings.auth.passHash` (scrypt), `settings.auth.ownerEmail`.
- Брокер: запись в `brokers[]` c `pinHash` (scrypt), `email`, `active`, `roleType`.
- Пароли — **только scrypt** (`hashPassword` формат `s2$salt$hash`); старые sha256 (`isLegacyHash`) авто-апгрейдятся при первом успешном входе. Чистые пароли не хранятся и не логируются; `pinHash`/`passHash` вырезаются из публичной выдачи (`brokerPub`, `publicSettings`).

## 2. Регистрация

`POST /auth/register` (rate-limit 20/час на IP):
1. Валидация e-mail + пароль ≥6.
2. Уникальность e-mail: `registry.byEmail[email]` → 409, если занят.
3. Новый `tid = t_<hex>`, `store.createTenant` (запись в `registry.tenants`), `registry.byEmail[email]=tid`.
4. В контексте тенанта: `ensureTenantDefaults` (инициализирует ~30 коллекций-массивов + `settings`), чистый старт (сброс demo-данных, оставляем цепочки+шаблоны), `passHash = hashPassword(pw)`, `ownerEmail`, запись `consent`.
5. Кука сессии `lumen_sid` (HttpOnly, SameSite=Lax, Secure на https, 30 дней) + `registry.sessions[sid]={tid}` + `settings.auth.sessions[sid]`.

Инвариант: неверный/битый ввод не создаёт «полутенанта» — тенант создаётся атомарно, дефолты гарантированы `ensureTenantDefaults`.

---

## 3. Вход

`POST /auth/login` (rate-limit `login:ip:email`):
- **По e-mail** (SaaS): находим тенанта через `registry.byEmail[email]` → в его контексте проверяем `passHash` (owner) ИЛИ `brokers[].pinHash` (broker). Апгрейд legacy-хэша на лету.
- Возвращаем куку `lumen_sid`; в `registry.sessions[sid]={tid}` и `settings.auth.sessions[sid]={role,brokerId,ip,ua,lastSeen}`.
- Роль сессии: owner / broker (реальные права брокера — из `roleType`).

Резолв тенанта на каждом запросе (`server/index.js` ~2664): cookie `lumen_sid` → `registry.sessions[sid].tid` → `store.enterTenant(tid)`. Публичные страницы без cookie — через `publicTenantFor(p)` (ищет владельца ресурса по id: `/p /c /mp /learn /cal /m /b`).

**Два хранилища сессий (важно понимать при правках):**
- `registry.sessions[sid] = {tid}` — глобальная карта sid→тенант (для резолва ДО загрузки БД).
- `settings.auth.sessions[sid] = {role, brokerId, ...}` — детали сессии внутри тенанта.
- **Гейт — это `getSession()`**, он проверяет `settings.auth.sessions[sid]`. Значит инвалидация сессии = удаление из `settings.auth.sessions` (registry-запись без per-tenant записи не пускает).

## 4. Смена и сброс пароля

- **Смена (в приложении)** `POST /auth/password` — роле-осознанная: owner меняет `passHash` (+ выкидывает все остальные свои сессии), broker меняет свой `pinHash`. Требует текущий пароль, новый ≥8.
- **Сброс (забыл пароль)** `POST /auth/forgot` → токен в `registry.resets` → письмо (Resend, если настроен) со ссылкой `/reset?token=`. E-mail-энумерация закрыта (всегда `{ok:true}`). `GET /reset` — форма; `POST /auth/reset` — ставит новый `passHash`/`pinHash` (owner или broker по e-mail), логинит.
- **Верификация e-mail** `POST /auth/verify` (+ `registry.verifs`).

---

## 5. Аккаунты брокеров внутри агентства

- **Приглашение** `POST /api/brokers/invite` (owner) → `registry.invites[token]={tid,brokerId,email}` → ссылка `/invite?token=`.
- **Принятие** `GET /invite` (форма) → `POST /auth/accept-invite` — брокер задаёт имя+пароль (≥6), ставится `pinHash`, `active=true`, логинится.
- **Права**: `roleType` брокера → `ROLE_CAPS` (что видит/может). Видимость лидов: own/all + фильтр по тегам/источникам. Гейт RBAC — на сервере (`nonOwnerBlocked`), не CSS.
- **Оффбординг**: `active=false` — вход закрывается (`x.active !== false` в проверках), лиды передаются; история сохраняется.
- **Просмотр как брокер** (owner): `POST /api/preview` (`previewAs`) — read-only, код доступа брокера скрыт.

## 6. Хранение данных

- **Per-tenant файл**: `DATA_DIR/tenants/<tid>/db.json` (лиды, переписки, брокеры, настройки, встречи и ~30 коллекций).
- **Глобальный реестр**: `DATA_DIR/registry.json` (тенанты, byEmail, sessions, invites, resets, verifs, adminSessions, adminKey, securityLog).
- **Атомарная запись**: tmp-файл + `rename` (частичной/битой записи при краше не бывает).
- **`data/` целиком в .gitignore** — рантайм-данные с секретами интеграций НИКОГДА не коммитятся (был инцидент: Twilio-ключ чуть не ушёл в git).
- ⚠️ Параллельные сессии могут писать секреты в primary `db.json` — не коммитить `data/`.

## 7. Сохранность данных (защита от «всё легло»)

Многослойная, именно против сценария дашборда:
1. **Атомарные записи** — краш при сохранении не бьёт файл.
2. **Гард PRE-WIPE** (`saveTenantNow`): если число лидов резко падает (>5 → 0 или <20% прежнего) — снимок `PRE-WIPE` ДО записи + предупреждение в лог. Ловит «обновление обнулило базу».
3. **Авто-восстановление**: при загрузке тенанта, если `db.json` повреждён/пуст, но тенант есть в реестре → восстановление из последнего валидного бэкапа (а НЕ пере-сид пустой базой). Проверено: битый db.json → рестарт → лиды на месте.
4. **Тиры бэкапов** (`store.backupTenant`): старт + **каждый час** (`auto`, последние 40 ≈ 40ч) + суточные (`daily`, 30 шт, не выпиливаются) + `PRE-WIPE`/`PRE-IMPORT`/`PRE-DELETE`/`PRE-RESTORE` (safety-теги, НИКОГДА не прунятся). Восстановление в 1 клик (`/api/backups/restore`, перед откатом — `PRE-RESTORE`).
5. **Офф-сайт** (опц.): `BACKUP_WEBHOOK_URL` — суточная выгрузка наружу (защита от сбоя тома).
6. **Целостность источника**: битый файл-источник не попадает в бэкап (пропускается).

## 8. Безопасность доступа
- scrypt-пароли, HttpOnly+SameSite+Secure куки, rate-limit на всех auth-роутах, анти-энумерация e-mail.
- Изоляция тенантов (ALS-контекст; кросс-тенант доступ невозможен — проверено 83/83 saas-auth + 34/34 pentest).
- **Детектор аномалий** (`secSignal`): всплески 401/403, брутфорс админ-ключа, чужой TG-secret, экспорт/удаление → журнал `registry.securityLog` + алерт основателю + вкладка «Безопасность» в `/admin.html`.
- Заголовки: X-Frame-Options, X-Content-Type-Options, Referrer-Policy, CSP, HSTS (https).
- GDPR: экспорт (`/api/export`), удаление аккаунта (`/api/account/delete`, с PRE-DELETE бэкапом).

## 9. ⭐ Правила безопасных изменений (чтобы НИКОГДА не лечь)

Любая правка логина / сессий / хранения / правил доступа ОБЯЗАНА:
1. **Не менять форму существующих данных без миграции.** Новые поля — с дефолтом в `ensureTenantDefaults`, не ломая старые записи. Никогда не переименовывать/удалять поля, от которых зависит вход, без апгрейд-пути (как legacy-хэш → scrypt).
2. **Сохранять оба хранилища сессий синхронно** (registry.sessions + settings.auth.sessions). Гейт = `getSession` (per-tenant). Не «чистить» одно без понимания второго.
3. **Прогнать тесты ДО пуша**: `node test/saas-auth.mjs` (83 инварианта) + `node test/security-stress.mjs` (34 атаки) + `node test/smoke.mjs`. Красный тест = не пушим.
4. **Локальная проверка на чистом временном `DATA_DIR`** (не 5077 — там дев юзера): регистрация → вход → смена пароля → сброс → инвайт брокера → вход брокера.
5. **Сначала бэкап, потом рискованная операция.** Массовые изменения данных — только после `backupTenant(tid,'manual')`. Гард PRE-WIPE — страховка, а не разрешение на неаккуратность.
6. **Пуш = деплой Railway.** Коммить свободно, пушить ПАЧКОЙ после локальной проверки. Клиентские/рисковые правды (вход/оплата) — отдельным осознанным пушем.
7. **Инвариант входа**: «страница с данными ⇔ валидная сессия; иначе — окно входа, НИКОГДА молчаливый пустой каркас». Правка не должна давать пустой экран без сессии.
8. **Изменения правил доступа** — покрывать тестом на изоляцию (чужой тенант/чужая роль → 403), иначе можно открыть данные чужому агентству.
